# /anniv-sns-batch｜SNS原稿の隔週バッチ生成

X と Threads の投稿原稿を**隔週で13本**（X 6本・Threads 6本・予備1本）まとめて作り、
`anniv-tool.date/posts/inbox`（受信箱）に貼り付ける JSON を出す。

```
このスキル ──▶ JSON ──▶ 受信箱に貼る ──▶ 人が1本ずつ承認 ──▶ 週3の枠へ自動で予約 ──▶ cron が投稿
```

**承認は必ず人が通す。** このスキルは原稿を作るところまでで、投稿はしない。

## 前提（読む順に）

| ファイル | 何のため |
|---|---|
| `記事管理/SNSネタ台帳.csv` | **ネタのSSOT。** 空きマスと使用済みはここが持つ |
| `メディア方針/SNS戦略.md` 3〜4章 | 面ごとの役割と、狙う行動（送信・保存） |
| `メディア方針/投稿台本.md` 6章 | X原稿バンク20本＝**文体の見本** |
| `.claude/agents/reference/content-axis.md` | 軸1（gift）／軸2（date）／軸3（concierge）の定義 |

**`article-style-guide.md` は読まない。** あれはSEO記事のルールで、SNSには適用しない
（2026-08-31にユーザーが決定）。SNSの主眼は**寄り添うことと引き付けること**なので、
記事側で禁じている断定や煽りは使ってよい。守るのは下の「3つだけ」。

---

## 守る3つだけ

1. **X にリンクを入れない。** X はリンク付き投稿が $0.20（リンク無しの13倍）。
   受信箱がエラーで弾くので入れても取り込めない。**Threads はリンクを貼ってよい**
2. **実績の量・年数を暗示しない。** 「手がけてきた」「多数の実績」は立ち上げ期なので事実として嘘になる
3. **Anniv という役務そのものの効果は保証しない。**
   「このプレゼントは絶対に喜ばれます」は主観の表明として通る。
   「Anniv に頼めば必ず成功します」は役務の効果の断定で景表法（優良誤認）に触れうる

これ以外は自由。「絶対に喜ばれる」「失敗しない」のような**一般論としての断定は使ってよい**。

---

## 口調

**相談相手としての敬体。** 「〜なんです」「〜が多いです」「〜してみてください」。

- 共感から入ってよい（「毎年悩みますよね」のような1行を頭に置いてよい）
- 抽象語で始めてもよい
- 言い切りで閉じなくてよい。問いかけで終わってもよい
- 絵文字は使わない。強調は語順と改行でやる
- 専門用語を出さない。出すなら必ずその場で言い換える

**「実は」「意外と」で始めるのは3本に1本まで。** 敬体だと全部これで始めたくなり、
バッチ13本が同じ顔になる。

### ★ 1行目からヘッジを全部抜く（2026-08-31 に踏んだ）

敬体で書くと**語尾を丸めたくなる**。丸めた瞬間にフックが死ぬ。
**次の言葉は1行目で禁止**（2文目以降なら使ってよい）:

> ことが多いです ／ たいてい ／ ほとんどが ／ と思います ／ だったりします ／
> かもしれません ／ 割と ／ 意外と ／ 〜のほうが多い

- ✗ 「サプライズがバレる原因、中身より袋のことが多いんです。」
- ✓ 「サプライズは、中身を開ける前にバレています。」

**敬体でも断定はできる。** 一般論の断定は解禁されている（「守る3つだけ」参照）ので、
1行目では言い切る。ヘッジは2文目に置けばいい。

## 型

### X（1本 45〜90字・改行なし・リンク禁止）

`投稿台本.md` 6章のX原稿バンク20本が完成した見本。**あれと同じ密度で書く。**

```
[1文目] 状況の名指し。数字か固有名詞を1つ入れる
[2文目] なぜそうなるかの理由。観察できる事実で示す
[3文目] やることを1つ。または問いかけ（省略可）
```

**目安130字・上限280字**（アプリの数え方はコードポイントだが、Xの実仕様はCJK 2文字。
130を超えると実仕様の上限に近づく）。実際は45〜90字に収める。

### Threads（1本 160〜220字・1行目だけ改行・リンク可）

```
[1行目] フック。ここだけ改行する
[2文目以降] 改行せず1段落で続ける
```

**1行目で答えを言わない。** Threads は折りたたみで1行目しか見えないので、
これが2文目を開かせる唯一の仕掛け。**ただし「見出し」を置くのとは違う。**
結論の断定だけ置いて、理由を2文目へ送る（下の「フックの5型」）。

4文の役割：

| | 役割 | 中身 |
|---|---|---|
| 1文目 | **フック** | 対象者が「自分のことだ」と気づく。数字か固有名詞を1つ |
| 2文目 | **理由** | なぜそうなるかを観察できる事実で示す。**ここが実績の代わりの信用** |
| 3文目 | **順番の指摘 or 逆張り** | よくある手順を名指しして違いを示す。**適度に人を刺してよい** |
| 4文目 | **置き換え or 問いかけ** | やることを1つ。または疑問形で締めてコメントを誘う |

**上限500字**（URLも字数に含まれる）。

---

## フックの5型（1行目の作り方）

**「え？」と言わせられなければフックではない。** 説明の見出しを1行目に置くと必ず滑る
（「聞いておきたいことが3つあります」は見出しであってフックではない）。

| | 型 | 作り方 | 例 |
|---|---|---|---|
| **1** | **常識の否定** | 「〜ではありません」で、思われている原因を先に潰す | 検索履歴を消しても、サプライズはバレます |
| **2** | **数字の前倒し** | 2文目に書きたくなる数字を1行目へ上げる | サプライズプレートは、16文字目から崩れます |
| **3** | **逆説** | 「〜するほど〜」「〜と言う人ほど〜」 | 3年目の記念日は、頑張るほど外します |
| **4** | **手遅れの宣告** | 「その時点でもう〜」と、過ぎた一線を告げる | 2時間制のお店を取った時点で、ゆっくり話す時間は消えています |
| **5** | **意外な主語** | 答えを人・物・値段にすり替える | 部屋の飾りつけでいちばん効くものは、無料です |

**3案は「同じネタで違うフック型」を試す。** 5型から3つ選んで書き、採点で選ぶ。
切り口（見落とし／順番／逆張り）は本文の組み立ての話で、**フックとは別の軸**。

### 自己チェック

**1行目だけ読んで「知ってる」と思ったら書き直す。** 3秒で判定できる。
「なるほど」もダメで、要るのは「え？」。

## 自己採点（各20点・合計100点）

| 軸 | 見るところ |
|---|---|
| **フックの強さ** | **1行目で「え？」と言わせられるか。** 説明の見出しになっていないか。ヘッジが混ざっていないか |
| **自分ごと化** | 対象者が「自分のことだ」と気づく指定があるか（同棲中／3年目／付き合いたて） |
| **理由の具体性** | 数字・観察できる事実で説明できているか |
| **信用** | 実績を語らずに提案力が伝わるか |
| **送信・保存の動機** | 「これ気をつけて」と人に送りたくなるか（IG/Threadsはここが重い） |

**フックの強さが14点未満の案は採用しない。** 他の4軸が満点でも落とす。
2026-08-31 の初回バッチが13本ぜんぶフック落ちしたのがこの規定の理由で、
原因は「敬体に寄せた結果、1行目まで丸めた」こと。

**最高点の案を採用する。** ただし同点なら A → C → B の順で選ぶ（見落とし型がいちばん安定する）。
不採用の2案も `note` に1行で残す（次回の材料になる）。

## 手順

### Step 0. 前回の反応を読む

`C:\dev\multi-SNS-manager` で実行する。**読み取りだけ。**

```bash
npx wrangler d1 execute multi-sns-manager-db --remote --json --command "SELECT p.idea_key, p.scheduled_at, t.post_type, m.impressions, m.likes, m.comments, m.shares, m.saves, m.age_ms FROM posts p JOIN post_targets t ON t.post_id = p.id JOIN post_metrics m ON m.post_target_id = t.id WHERE p.source = 'intake' AND t.state = 'published' ORDER BY p.scheduled_at DESC, m.age_ms DESC LIMIT 60"
```

出たら**ユーザーに要約を返す**（数字の羅列は返さない）：

- 上位3本と下位3本。**絶対値ではなく順位で見る**（`SNS戦略.md` 7章）
- 上位に共通していた要素（型A/B/C・工程・状況・軸・文の長さ）
- 今回の生成でどう振るか（例：「逆張り型が上位を占めたのでC案の比率を上げる」）

**まだ1本も公開されていなければこのステップは飛ばす。** 初回はそれが正常。

### Step 1. 台帳を読んで空きを出す

`記事管理/SNSネタ台帳.csv` を読み、次を出す。

- **未使用のネタ**（`X使用日` と `Threads使用日` が両方空）
- **空きマス**（「工程 × 状況」で1本も無い組み合わせ）

> 2026-08-31 時点の穴：**工程「残す」が0本**、状況「付き合いたて」「同棲」が0本。
> ここから埋めると被りが出にくい。

**同じ `idea_id` を X と Threads の両方で使ってよい**（型が違うので別物になる）。
ただし**同じ面で90日以内に再利用しない**。

### Step 2. 自問自答でネタを足す

未使用が13本に足りなければ、**空きマスを3〜5個提示してユーザーに質問する**。

外部への取材シートではなく、**その場でチャットで答えてもらう**
（プレゼント選定・演出をやっているのはユーザー本人。`interview-sheet.md` と同じ形）。

質問は「工程 × 状況」を具体的に指定して聞く。例：

> 「残す × 交際記念日」で聞かせてください。記念日が終わったあと、
> 写真や飾りやカードを「どうすると翌年に効く」と思いますか。逆に、
> やってしまうと何も残らないパターンはありますか。

**答えは1行の「一次知見」に落として台帳に追記する。** 抽象論は捨てる
（「思い出は大切」ではなく「カードは箱ではなく本に挟むと翌年に出てくる」のレベルまで削る）。

### Step 3. 生成

- **X 6本**（週3×2週）
- **Threads 6本**（週3×2週）
- **予備 1本**（どちらかの面で使う。承認で落ちたときの埋め）

各本で3案作って採点し、最高点を採用する。

**配分のルール**

- **軸**：軸1（gift）を半分、軸2（date）を1/3、軸3（concierge）を残り。軸3は受注直結だがKWが狭いので寄せない
- **切り口**：A/B/C を偏らせない。ただしStep 0で上位が偏っていればそちらへ寄せる
- **リンク（Threadsのみ・6本中2本まで）**
  - **1本は Instagram の特定の投稿へ**（その週のカルーセルの続きを見せる導線）。
    URLは `anniv-tool.date/posts` の各配信先にある「投稿を開く」から取る。
    **公開済みのIG投稿にしかURLは付いていない**（2026-08-31以降に出したものだけ保存される）ので、
    無ければユーザーに聞く
  - **もう1本はCTA**（`links` 経由。プロフィールのリンクと同じUTM付き）
  - **リンク付きは週1本に固定する。** Threadsでリンクがリーチを落とすかは未実測なので、
    残り2本と比べられる状態を保つ
- **CTAは6本に1本まで。** 毎回入れると広告アカウントに見える

### Step 4. ユーザーに見せる

生成した13本を**採用案だけ**並べて出す。1本につき：

```
[x-003] 軸1 / 工程=包む・仕込む / 状況=通年 / 型C（逆張り） / 82点
（本文）
　落とした2案: A=中身より袋の見落とし型(74) / B=順番の入れ替え(69)
```

ここでユーザーが直したいと言ったら**その場で直す**（受信箱に入れる前のほうが速い）。

### Step 5. 台帳を更新する

採用したネタの `X使用日` / `Threads使用日` に**予定日ではなく生成日**を入れる
（実際の投稿日は枠が決めるので、ここでは分からない）。
Step 2 で足したネタは行ごと追記する。

### Step 6. JSON を2つ出す

**X と Threads は `postType` が違うので別バッチ。** 2つ出す。

```json
{
  "batchId": "gen_2026-09a",
  "postType": "x_tweet",
  "items": [
    {
      "key": "x-001",
      "caption": "本文をそのまま",
      "ideaKey": "wrap-brand-paper-bag",
      "note": "軸1 / 包む・仕込む / 型C / 82点"
    }
  ]
}
```

- `batchId`: `gen_YYYY-MMa`（その月の前半）／ `gen_YYYY-MMb`（後半）
- `key`: `x-001` 〜 / `th-001` 〜。**バッチ内で一意**
- `ideaKey`: 台帳の `idea_id` をそのまま。**重複検知と次回の実績還流に使う**
- `note`: 承認画面に出る。軸・工程・型・点数を1行で

**Threads 側は `"postType": "threads_text"`。**

最後にユーザーへ渡す手順を書く：

> 1. `https://anniv-tool.date/posts/inbox` を開く
> 2. 「1. 取り込む」に上のJSONを貼って取り込む（**すべて下書きで入る。まだ出ない**）
> 3. 「2. 承認する」で1本ずつ読み、OKなら「承認して次の枠へ予約」
> 4. 承認した瞬間に次の空き枠へ予約が入る。カレンダーで確認できる

## 落とし穴

- **同じJSONを2回貼っても増えない**（`posts.id` が `projectId:batchId:key` から導かれている）。
  貼り直しは安全。ただし**`batchId` を変えると別物として増える**
- **URLをXの本文に入れると取り込めない**（エラーで弾かれる）。Threadsは通る
- **枠が未設定だと承認できない。** 受信箱の「3. 投稿枠」で先に登録する
  （既定は X 火木土 12:15 / Threads 月木金 20:00）
- **却下しても行は残る。** 同じネタが次回また出てこないように、却下したら台帳の
  `反応` に理由を1行書く
- **予約時刻ちょうどには出ない。** cronは「予約時刻を過ぎた最初の実行」で投稿するので数分ずれる
- **X は投稿ごとに $0.015 かかる。** 13本のうちXは6本なので隔週 $0.09。
  リンクを入れると1本 $0.20 に跳ねる（＝入れない理由）
