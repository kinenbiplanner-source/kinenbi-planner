# キーワード選定の判定基準（全軸共通・SSOT）

`/anniv-pick-keyword` と、KWの取捨を判断するすべての場面が参照する。**ここに書くのは全軸共通の判定手順だけ**。

- 軸ごとのテーマ範囲・リサーチ観点・CV先・想定読者の本体 → `.claude/agents/reference/content-axis.md`
- 勝てない領域・最大競合・着手順の本体 → `メディア方針/改良ロードマップ.md`「記事を書く」／`メディア方針/メディア戦略.md` 3章・7章
- 一次情報として書けることの範囲 → `.claude/agents/reference/社内ナレッジ.md`
- 記事の書き方（タイトルへのKW配置・H2へのサジェスト分散） → `.claude/agents/reference/article-style-guide.md` 6章・7章

このファイルは**それらの結論を判定手順に変換したもの**。軸固有の事実を書き足さない（更新は各SSOT側でやる）。
機械で判定できる部分は `src/lib/seo/` に写してある（要塞度＝`serp.ts`、カニバリ＝`cannibal.ts`）。**ルールを変えたらコードも直す**。

> 爆速開発部の `keyword-selection.md` を Anniv 向けに置き換えたもの。骨格（5観点・要塞度A/B/C・3判定）は同じで、
> 相手にする SERP の顔ぶれ（BtoB 比較ポータル → EC・予約DB）と CV（受託 → 無料相談）を差し替えている。

---

## 1. 判定の5観点

1本のKWを、この5つで見る。**①が満たせないKWは他が良くても採らない**（メディアの芯＝「実際にプレゼント選定・演出をプロデュースしている側が書く」がドメイン適合だから）。

| # | 観点 | 見るポイント | 落ちる例 |
|---|---|---|---|
| ① | **ドメイン適合** | 当事者として一次情報が書けるか。`社内ナレッジ.md` の判断・実際の依頼対応に接続できるか。**贈る相手が恋人・交際中カップルか**（メインターゲット） | 親・上司・友人・子供向けのギフトKW。商品スペックの比較だけになるKW |
| ② | **SERP占有主体** | 上位10を誰が占めているか（下の要塞度A/B/C） | EC・ギフトモールが要塞化している「◯◯ プレゼント おすすめ」。予約DBが独占する「◯◯ ディナー 個室 ＋エリア」 |
| ③ | **CV距離** | 流入が無料相談（`/apply`）に繋がるか。軸3 ＞ 軸2 ＞ 軸1、課題解決 ＞ 比較・検討 ＞ 集客 | 商品名を決めて買う直前の人（ECへ流れる）。DIY完結で誰にも頼まない人 |
| ④ | **リスク** | AdSense ポリシー（審査中）・景表法（Anniv の役務効果の断定）・実績を盛らないと書けないKW・18禁寄り | 「絶対喜ばれる」型のKW。「実績多数」を前提にするKW |
| ⑤ | **既存クラスタ接続** | 既存記事と内部リンクで束ねられるか。逆に**カニバらないか** | 同軸・同ファネル層で既存記事と検索意図が重なるKW |

⑤のカニバリは、台帳の `seed`（種KW）が同じ行を検索意図まで見て判定する。**同じ種KWでも切り口がズレていれば共存可**
（例：「記念日 レストラン 予約 いつから」＝時期／「記念日 レストラン 選び方 失敗」＝条件整理）。
`src/lib/seo/cannibal.ts` が dup / strong / weak の3段で機械判定を出す。**dup は無条件で落とす。strong は切り口をずらすか既存記事のリライトに振る。weak は人が見る**。

## 2. SERP要塞度（A / B / C）

上位10の**顔ぶれだけ**で機械的に分類する。記事の中身の良し悪しは見ない（それは執筆時の competitor-researcher の仕事）。

### 上位10の7分類（`src/lib/seo/serp.ts` の `DOMAIN_CLASSES` と対）

| 分類 | 何か | 代表ドメイン |
|---|---|---|
| **EC・ギフトモール** | 商品DBと購入導線で勝つ相手。ギフト系KWの要塞 | tanp.jp / giftmall.co.jp / anny.gift / giftpedia.jp / moodmarkgift.mistore.jp（伊勢丹）/ giftful.jp / rakuten.co.jp / amazon.co.jp / zozo.jp / shopping.yahoo.co.jp / bellemaison.jp / lohaco / hibiyakadan.com / nicoflor.jp |
| **予約DB・グルメ** | 予約在庫を持つ相手。レストラン・旅行系KWの要塞。**在庫を持たない立場では構造的に勝てない** | ozmall.co.jp / restaurant.ikyu.com / ikyu.com / tabelog.com / gnavi.co.jp / hotpepper.jp / retty.me / hitosara.com / jalan.net / travel.rakuten.co.jp / rlx.jp（Relux）/ booking.com / tablecheck.com / anniversary.ozmall |
| **ランキング・比較まとめ** | 専業アフィリ・比較メディア | my-best.com / kakaku.com / sakidori.co / 4meee.com / oggi.jp / precious.jp / ranking.goo.ne.jp / kurashi-no.jp / limia.jp |
| **単社オウンド** | 事業会社の自社メディア（＝自分たちと同じ立場）。花屋・ジュエリー・写真館・単館レストラン・ホテル・サプライズ業者の記事 | 業種で判断（ドメインで固定できない） |
| **公式** | ブランド・ホテル・店舗の公式ページ、官公庁 | 同上 |
| **個人ブログ・Q&A** | 個人運営、知恵袋 | note.com / ameblo.jp / hatenablog / chiebukuro.yahoo.co.jp / oshiete.goo.ne.jp / okwave.jp / hatena / fc2 / livedoor |
| **SNS・動画** | | instagram.com / x.com / twitter.com / youtube.com / tiktok.com / pinterest.jp / threads.net |

判断がつかないものは「不明」として件数に入れる（推測で分類しない）。

### 判定

**要塞側の件数 ＝ EC・ギフトモール ＋ 予約DB・グルメ ＋ ランキング・比較まとめ** の合計で分ける。

| 要塞度 | 条件 | 判断 |
|---|---|---|
| **A＝要塞** | 要塞側が**6件以上** | 単社オウンドが刺さらない。正面から入らない |
| **B＝割り込み可** | 要塞側が**3〜5件**、または単社オウンド・個人ブログ・Q&Aが混在して分散している | 一次情報があれば割り込める。**主戦場** |
| **C＝空白** | 要塞側が**2件以下**、専門メディアが不在 | 最優先。ただし**需要そのものが無い可能性を必ず疑う**（4章の数字で裏を取る） |

判定を上書きする補正：

- **予約DB・グルメが3件以上** → 要塞側の合計に関わらず **A**。予約在庫が無いと順位を取っても行動が完結しない（`改良ロードマップ.md`「勝てない領域」の実査結果）
- **公式が3件以上** → 情報の出所が固定されていて差別化しづらい → **A寄り**に倒す
- **個人ブログ・Q&A が5件以上** → 誰も本気で書いていない → **C寄り**に倒す（需要の裏取りは必須）
- 上位が**2024年以前の記事ばかり** → 鮮度だけで割り込める → **B寄り**に倒す
- **anny.gift が上位にいる** → 要塞度に関わらず「実務ディテール（段取り・締切・交渉・当日の時間割）で勝てるか」を必ず判定に添える。anny はガイド記事を量産中で内容も良い。アイデア列挙で並ぶと負ける
- Aでも**「段取り・交渉・手続き」切り口や「代行」切り口でクエリをずらせる**なら、ずらした先のKWで再判定する（「ホテル 飾り付け 許可」「レストラン サプライズ お願い 伝え方」がこの型。上位が個人ブログ・知恵袋レベルになる）

## 3. KWパターン → ファネル層

台帳の `funnel` 列は3値（集客／比較・検討／課題解決）。KWの語尾パターンで機械的に割り当てる。**判定に迷ったら検索意図（誰が何のために調べたか）を優先**する。

| ファネル層 | KWパターン | 役割 |
|---|---|---|
| **集客** | とは／アイデア／例／いつから／何日前／タイミング／相場／予算／飾り付け／メッセージ／過ごし方 | 入口。母数・認知。**無料相談には直接繋げない**。軸2・軸3への内部リンク元 |
| **比較・検討** | 比較／違い／ランキング／おすすめ／プラン／料金（軸3）／サービス／どっち | 橋渡し。判断軸を渡す |
| **課題解決** | 選び方／失敗／注意点／伝え方／頼み方／お願い／センスない／選べない／間に合わない／忙しい／ネタ切れ／嫌いな人 | 変換器。**無料相談 CV 直結。一次知見の差別化はここ** |

同じ語でも軸で層が変わる。「相場」は軸1（プレゼントの相場＝集客）と軸3（代行の料金相場＝比較・検討）で別物。「おすすめ」は軸1では EC の要塞なので原則採らず、軸3の「代行サービス おすすめ」は比較・検討として採る。

## 4. 需要の数字（どれを信じるか）

ボリュームは**取れる手段が日によって違う**ので、出どころを台帳の `volume_source` に必ず残す。上ほど信頼できる。

| 優先 | 出どころ | 何が分かるか | 台帳の列 |
|---|---|---|---|
| 1 | **Ahrefs**（MCP が繋がっているとき） | 月間検索数の実数・KD・トラフィックポテンシャル | `volume_num` / `kd`（`volume_source=ahrefs`） |
| 2 | **手動CSV**（キーワードプランナー／ラッコ） | 実数またはレンジ | `volume_num`（`volume_source=csv`。レンジは下限） |
| 3 | **Search Console の表示数** | 既に露出している領域の需要だけ | `volume_num`（`volume_source=gsc`） |
| 4 | **需要スコア**（サジェスト深度） | **候補どうしの相対順位だけ**。絶対量は分からない | `demand_score` |

- **需要スコアは絶対量を語らない**。「候補20個の中で上から何番目か」にしか使わない。スコアが高い＝検索されている、ではあるが件数は分からない（`src/lib/seo/demand.ts` の冒頭に式）
- **サジェストに出る＝需要の証拠、ではない**。サジェストは「検索されたことがある」しか示さない
- 1〜3 のどれも取れず、需要スコアも低い（下位1/3）→ **需要が確認できない＝保留**。勝ち筋にしない
- Ahrefs の数字が取れたら、それ以前の `volume_source` は上書きしてよい（上位のソースが常に勝つ）

## 5. 除外ルール

**全体除外**（`改良ロードマップ.md`「勝てない領域」＝調査で確定済み）：

- 「プレゼント おすすめ／ランキング／相場」系 → TANP・ギフトモール・伊勢丹が自社調査データで独占
- 「記念日ディナー 個室／夜景 ＋エリア」系 → OZmall・一休の予約DBが独占。予約在庫を持たない立場では構造的に無理
- 贈る相手が**恋人・交際中カップルでない**KW（親・上司・友人・子供・同僚・退職祝い）。メインターゲット外（メディア戦略.md 3章）
- 「代行」が**EC物流の発送代行・買い物代行に取られる**KW（軸3で検索意図がズレる。「プレゼント 代行 購入」「ギフト 発送代行」等）
- 18禁寄りの表現が要るKW／実績を盛らないと書けないKW／Anniv の役務効果を断定しないと成立しないKW

**軸ごとの除外**は `content-axis.md` 該当軸の「テーマ範囲」の外側を**その都度読んで当てる**。ここに転記しない（二重管理で古くなるため）。

**非採用が確定しているジャンル**：結婚式・プロポーズの本体（ゼクシィの要塞。「プロポーズ 演出 代行」のような代行切り口だけ軸3で検討可）／夫婦・結婚記念日（今は狙わない。メインターゲットを恋人に絞っている間は保留）。

## 6. 判定の出し方

5観点と要塞度を当てて、KWを3つに振り分ける。**「書かない」を明示的に出すのが選定の仕事**（勝てないKWを事後の診断で見つけるのでは遅い）。

| 判定 | 条件 | 次のアクション | 台帳 |
|---|---|---|---|
| **勝ち筋** | ①ドメイン適合あり かつ 要塞度B/C かつ 需要が確認できる（4章の1〜3か、需要スコア上位） かつ カニバリが dup/strong でない | `/anniv-write-article` へ | `status=todo` で登録（`verdict=win`） |
| **保留** | ①はあるが要塞度A、または需要が確認できない、または カニバリ strong で切り口をずらせるか未検討 | 寝かせる。**クエリをずらせないか再検討** | `status=todo` `priority=3` で登録（`verdict=hold`）。note に保留理由 |
| **書かない** | ①ドメイン適合なし、または 要塞度A かつ 一次情報で殴れない、または 除外ルールに該当、または カニバリ dup | 登録しない。**理由を1行で残して差し戻す** | 登録しない（`verdict=drop`） |

**要塞度Aかつ一次情報で殴れない＝差し戻し**。忖度して B に倒さない。「ギフト おすすめ」系に正面から入って EC に沈むのを、この関門だけが防ぐ。

---

## 7. 優先順位

「勝ち筋」が複数あるときの並べ方。上から順に効く。

1. **既存クラスタを補強するもの** — 同じ `seed` の記事が既にある領域に足す。内部リンクで束ねられるぶん立ち上がりが早い（`src/lib/seo/internal-links.ts` が「どこから張れるか」を出す）
2. **CV距離が近いもの** — 課題解決 ＞ 比較・検討 ＞ 集客。軸3 ＞ 軸2 ＞ 軸1。ただし**軸3はSERPがほぼ空白なので、需要の裏取りを必ず添える**
3. **要塞度C ＞ B** — 空白地帯を先に埋める
4. **需要が大きいもの** — 4章の数字で。**第1基準にしない**（同点のタイブレーク）
5. **軸の在庫が薄いもの** — 候補が枯れている軸を優先し、特定の軸だけ書き続ける偏りを防ぐ

**新規KWより既存記事のリライトが上に来る場合がある**：GSCで「表示は多いのにCTRが低い」「順位4〜20」のクエリは、新規を1本書くより既存記事に手を入れる方がROIが高い。`記事管理/PVレポート/現状ファクトシート.md` の「取りこぼし」「striking distance」を必ず突き合わせる。**GSC に台帳にも記事にも無いクエリが出ていたら、それは新KW候補**（ファクトシートの「未カバーのクエリ」）。

## ルールの所在（SSOT）

- 軸の定義・リサーチ観点・CV先：`.claude/agents/reference/content-axis.md`
- 勝てない領域・最大競合・着手順：`メディア方針/改良ロードマップ.md`「記事を書く」／`メディア方針/メディア戦略.md` 3章・7章
- 記事の共通ルール（タイトル・見出しのKW配置）：`.claude/agents/reference/article-style-guide.md`
- 一次情報として書けることの範囲：`.claude/agents/reference/社内ナレッジ.md`
- KW台帳：D1 `keywords`（`/admin/keywords`。CSV は `記事管理/KWマスターDB.csv` に派生）
- GSC実データ（需要の代理指標）：`記事管理/PVレポート/現状ファクトシート.md`（`/anniv-update-pv` が再生成する）
- 機械判定の実装：`src/lib/seo/serp.ts`（要塞度）／`cannibal.ts`（カニバリ）／`demand.ts`（需要スコア）／`internal-links.ts`（内部リンク）
