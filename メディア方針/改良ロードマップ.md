## Git 運用のメモ

`master` が本流でリモートのデフォルトブランチ（2026-08-26 に `main` から変更。`main` はGitHubのWeb UIから `index.html` を1つアップしたときにできた履歴の繋がらない孤立ブランチだったので削除した）。

push は Git Credential Manager がGUI認証を出すので、**手元のターミナルで実行する必要がある**（自動実行では認証待ちで止まる）。

作業ブランチを master へ寄せるときは、**checkout せずにリモート側を進める**のが安全（別セッションの未コミット変更があると `git checkout master` が弾かれるため）：

```bash
git push origin feat/astro-media:master
```

## すぐやる（ダッシュボード操作）

Cloudflare / Google の管理画面での作業で、CLIからは代行できない。

### 1. Access に `/dashboard` を追加　済（2026-08-26）

### 2. Search Console に sitemap を登録し直す　済（2026-08-26）
`sitemap.xml` を送信し、トップと `/media` の再クロールもリクエスト済み。

**記事0本のいま、検出されるURLは4件（`/`・`/privacy`・`/tokutei`・`/media`）で正常。** `sitemap.xml` は毎回D1を読むので、記事を公開すれば自動で増える。**再送信は不要**。

### 3. GA4 のキーイベント設定　済（2026-08-26）
`form_complete` と `line_add_click` をキーイベントとしてマーク済み。あわせて `follow_click` の着弾も本番のリアルタイムレポートで確認した。詳細は `計測設計.md` 6章。

### 4. www → apex の Redirect Rule　**ルールは作ったが壊れている。要修正**
2026-08-26 にルールを作成したが、**リダイレクトの「種類」が静的（Static）のまま**で、式が評価されず文字列としてそのままURLに入っている。結果 `https://www.anniv.gift/concat("https://anniv.gift", ...)` へ飛び、**www 全体が無限リダイレクトループ**になっている（ルール作成前は200を返していたので、状態としては悪化）。

Rules → Redirect Rules → 該当ルールを編集
- If: Custom filter expression → Hostname **equals** `www.anniv.gift`
- Then: **種類を「動的（Dynamic）」に変える**（ここが肝）／式 `concat("https://anniv.gift", http.request.uri.path)` ／ **301** ／ Preserve query string にチェック

> **静的（Static）だと入力値がそのままリダイレクト先の文字列になる。** パスを引き継ぐには動的（Dynamic）が必須。すぐ直せないときは、ひとまずルールを**無効化**してループを止める。

> Worker側では直せない。Astro の Cloudflare アダプタが**静的アセットを先に返してから Astro 本体を呼ぶ**ため、`/` や `/contact` には middleware が効かない（`run_worker_first` でも解決しなかった）。

### 5. Tally のリダイレクト先を確認　済（2026-08-26）
対象フォームは `https://tally.so/r/lbVDPB`。送信後のリダイレクト先を拡張子なしの `https://anniv.gift/thanks` に揃えた。

### 6. Vercel の後片付け　済（2026-08-26）
Vercel のプロジェクト、ワイルドカード `*` Aレコード2件、`_domainconnect` CNAME をすべて削除。リポジトリの `vercel.json` も消した（`cleanUrls` 相当は `wrangler.jsonc` の `html_handling` が引き継いでいる）。

存在しないサブドメイン（例 `zzztest123.anniv.gift`）が NXDOMAIN になり、apex が Cloudflare のIPを返し続けていることを確認済み。

## 改良（効果が大きい順）

### A. アイキャッチ画像の運用を決める
R2アップロードは実装済みなので、あとはテンプレを決めるだけ。**一覧のCTRに直接効く**ので記事が数本たまる前にやりたい。

> 繋ぎとして、アイキャッチ未設定のカードは**軸で地の色・記事idでグラデーションの角度**を変えるようにした（`media.css` の `.card-thumb.is-empty.is-*`）。全カードが同じ絵になる問題は消えたが、**実画像の代わりにはならない**。テンプレが決まったらこのCSSは消せる。

### B-2. 計測をダッシュボードに集約　済（2026-08-28）
自前計測（`/api/ev` → `event_daily`）とGA4 Data API（`/api/ga4`）を `/dashboard` の Measurement 欄に集約した。
UTM規約・実装・GA4のサービスアカウント設定はすべて `計測設計.md` 7・8・11章にある。

- **流入元別に「クリック総数／うちCV」が並ぶ**ので、来ているのにCVしない流入元がすぐ分かる
- 自前とGA4は**列を分けて出す**（必ずズレるので足さない・突き合わせない）
- **残っているのは「どの記事から相談に来たか」**。今は `utm_source` までしか分からない。
  記事内のCTAリンクに `utm_campaign=<slug>` を足すのが最小の追加（`計測設計.md` 10章）
- **SNS側の指標（フォロワー推移・投稿別）の合流は未着手**。`SNS_DB` バインディングで
  読める経路はあるが、**multi-SNS-manager 側の Instagram インサイトが実API未検証**なので待ち

### B. PVの推移グラフ　済（2026-08-26）
`/admin/stats`（管理画面ヘッダーの「メディア分析」）として実装。日次PVの棒＋7日移動平均（30日/90日切替）、記事別の直近28日 vs 前28日、軸別カバレッジ、月別の公開ペース。

- リライト候補は自動で印が付く（**下降**＝直近28日が前28日の70%未満／**伸び悩み**＝公開45日超で直近28日が20PV未満）。しきい値は `src/lib/stats.ts` の定数。立ち上げ期の暫定値なので、記事が20本を超えたら実データを見て決め直す
- 計測開始から28日たつまでは判定を出さない（古い記事が「PVが無い＝伸び悩み」に見えるため）
- ここのPVは `/api/pv` のビーコンで数えた自前の値。GA4とは必ずズレるので、突き合わせない

### C. 下書きのプレビューURL
今は公開しないと本番の見た目を確認できない。`?preview=<トークン>` で下書きを本番レンダリングで見られるようにすると、公開前チェックが確実になる。

### D. 内部リンクの自動提案
今は anniv-write-article が `KWマスターDB.csv` を見て手動で候補を出している。記事が10本を超えたあたりから、**D1の記事から関連度の高いものを自動提案する**仕組みが効いてくる。

> エディタ側は先に入れた：ツールバーの「内部」から公開済み記事を検索して、style-guide 11章の文型（段落を分けた誘導文＋アンカーは記事タイトル）ごと差し込める。本文中の `/media/<slug>` が実在するかも公開前チェックで見る。**残っているのは「どの記事を貼るべきか」の提案**（軸・KWの近さから候補を出す部分）。

### E. 使われなくなったCSSの掃除
メディアUI刷新で `article.css` の一部（`.article-layout` `.article-side` `.toc-card` `.badge` など）が未使用になった。記事レイアウトは `media.css` の `.art-*` に移っている。動作に影響はないが、放置すると次に触る人が混乱する。**削除前に必ず使用箇所を精査すること**（クラス名が部分一致するので単純grepでは判定を誤る）。

### F. 一覧系ページの構造化データと薄いページ対策　済（2026-08-26）
メディアTOP＝`Blog`＋`BreadcrumbList`、カテゴリ＝`CollectionPage`＋`BreadcrumbList`、ページ送り＝`BreadcrumbList`。記事（`Article`＋`BreadcrumbList`）と合わせて全ての面が揃った。パンくずの表示も4種類すべてに入れてある。

- **記事0本のカテゴリは `noindex`**。中身が「準備中」だけのページを検索結果に出しても評価が下がるだけなので、記事が入るまで伏せる。`sitemap.xml` 側も同じ条件（公開記事のある軸だけ）で出し分ける
- 記事が1本でも入れば自動で index に戻る。**手で戻す作業は不要**

### G. AIクローラ設定の再判断（3〜6か月後）
2026-08-26 に Cloudflare の「管理された robots.txt」をオフにして、AI検索に拾わせる方針にした。**実際にAI経由の流入が出るか、逆に引用されず取られるだけかはデータを見てから判断し直す**。

### H. AdSense の審査を通す　**受け皿は実装済み。審査は記事を公開してから**
2026-08-28 に「AdSense はやる」と決めて、コード側の受け皿を入れた（`src/lib/ads.ts` / `AdSlot.astro` / `MediaArticle.astro` / `media.css`）。プライバシーポリシー8章の追記も済み。
**`src/lib/ads.ts` の `ADSENSE_CLIENT` が空のあいだは、スクリプトも枠も1つも出力されない**ので、このまま置いておいて害はない。

残っているのはダッシュボード側の作業だけ。手順の全文は `収益化メモ.md` 3章。

1. **記事を3〜5本公開する（これが最大の関門）。** 記事0本のまま申請しても落ちる
2. AdSense に登録 → `https://anniv.gift` を追加
3. 所有権確認は **ads.txt スニペット方式**を選ぶ（メタタグ／コードスニペット方式だとLPの素のHTMLに広告用JSを貼ることになるので選ばない）→ `public/ads.txt` を作ってデプロイ
4. 審査申請（数日〜2週間）
5. 通ったら広告ユニットを2つ作る（記事末尾＝レスポンシブ／左サイド＝160×600）
6. `src/lib/ads.ts` にIDを入れてデプロイ
7. PageSpeed Insights で記事ページのCLSを測り直す

> **自動広告（Auto ads）はオンにしない。** 挿入位置をGoogleに任せるとCLSと本文の読みやすさが制御できなくなる。枠は `ads.ts` で定義した2つだけ。

### I. アフィリエイトの判断
`収益化メモ.md` 4章に候補と前提を整理済み。**AdSense とは独立に、記事数が積み上がるまで判断しない**。
