# Anniv 計測設計（SSOT）

最終更新: 2026-08-28（リンク設計＝UTM規約を確定、自前計測 `/api/ev` とダッシュボード集約を実装）

**このファイルは「今どう計測されているか」だけを書く。** 実装を変えたらここも必ず更新する。
記事・SNSの成果判断はすべてこの設計に依存するので、**新しいCTA・導線を足したら必ず対応するイベントも足す**。

## 1. なぜこれが要るか

爆速開発部メディアは月3万PVまで伸ばしたのに、外部リンククリック計測・内部CTAのイベントが未整備で
**「送客の成果が測れていない」状態のまま止まった**（同メディア戦略 6章）。
Annivは記事0本・SNS投稿ほぼ0本の段階で先に計測を通し、同じ轍を踏まない。

## 7. リンク設計（UTM）

**SNSの成果はここでしか分けられない。** UTMが付いていない流入は referrer からの推定に落ちるが、
Instagramのアプリ内ブラウザは referrer を落とすことがあるので、**推定は当てにしない**。
SNSに貼るリンクには必ずUTMを付ける。

### 規約

| パラメータ | 取る値 | 意味 |
|---|---|---|
| `utm_source` | `instagram` / `x` / `tiktok` / `line` / `meta_ads` | **どの媒体から来たか** |
| `utm_medium` | `profile` / `story` / `post` / `dm` / `bio` / `paid` / `qr` | **その媒体のどこに置いたリンクか** |
| `utm_campaign` | 投稿日 `20260907` など | **どの投稿から来たか。投稿台本のカレンダーと1対1にする** |
| `utm_content` | 任意（広告のクリエイティブ識別） | A/Bを分けるときだけ使う |

- **値は増やさない。** `utm_source` と `utm_medium` は `src/pages/api/ev.ts` の許可リストに閉じてあり、
  **知らない値は `other` に畳まれて記録される**。新しい媒体を使うときは、あちらの
  `ALLOWED_SOURCES` / `ALLOWED_MEDIUMS` に足してから使う（足さないと個別に数えられない）
- **`utm_campaign` は投稿日（YYYYMMDD）で統一する。** 台本のカレンダーと突き合わせられるので、
  「どの投稿が相談に繋がったか」が1クエリで分かる

### 実際に貼るURL

| 置き場所 | URL |
|---|---|
| Instagram プロフィール | `https://anniv.gift/links?utm_source=instagram&utm_medium=profile` |
| X プロフィール | `https://anniv.gift/links?utm_source=x&utm_medium=profile` |
| Instagram ストーリーズ | `https://anniv.gift/links?utm_source=instagram&utm_medium=story&utm_campaign=<投稿日>` |
| ストーリーズから記事へ直接 | `https://anniv.gift/media/<slug>?utm_source=instagram&utm_medium=story&utm_campaign=<投稿日>` |
| ストーリーズから相談へ直接 | `https://anniv.gift/contact?utm_source=instagram&utm_medium=story&utm_campaign=<投稿日>` |
| X の投稿（**月4本まで**） | `https://anniv.gift/media/<slug>?utm_source=x&utm_medium=post&utm_campaign=<投稿日>` |
| Meta広告 | `https://anniv.gift/contact?utm_source=meta_ads&utm_medium=paid&utm_campaign=<キャンペーン名>&utm_content=<クリエイティブ>` |

> **Xの投稿にリンクを貼ると API 課金が $0.015 → $0.20 になる**（13倍）。
> プラットフォーム側でもリンク付きはリーチが落ちる。**リンクはプロフィールと固定ポストに寄せる**
> （`メディア方針/SNS戦略.md` 3章）。

### 流入元は最初の着地で決まり、セッション中は引き継がれる

`/assets/track.js` が着地時にUTMを `sessionStorage` に入れ、**そのセッションの以降のイベント全部に添付する**。
`/links` にUTM付きで着地 → LINEをクリック、という流れで **LINEクリックにも `instagram/profile` が乗る**。

- **URLにUTMがあれば必ず上書きする**（first-touch にしない）。プロフィールから入り直したときに
  古い流入元が残ると、どの投稿から来たか分からなくなるため
- UTMが無いときだけ、保存済み → referrer 推定 → `direct` の順で埋める

**2026-08-28 にすべて実施済み。** Instagram・X のプロフィールURLも差し替え済みで、
**本番で `page_view` → `line_add_click` が `instagram / profile` を保ったまま記録されることを実測した**
（着地からLINEクリックまで流入元が繋がっている）。

## 8. 自前計測とダッシュボード（2026-08-28 実装）

**GA4の数字はGA4の画面にしか無い。** `/dashboard` に出す数字は自前で持つ。
記事PV（`pageviews`）で先に採った方針を、導線イベント全体に広げたもの。

### 流れ

```
ページ（LP・メディア）
  └ /assets/track.js  … UTM保持・page_view・クリックの委譲リスナー
        └ POST /api/ev … 正規化して D1 に日次で加算（event_daily）
              └ GET /api/insights … 集計して返す
                    └ /dashboard の Measurement 欄
```

| 部品 | 役割 |
|---|---|
| `public/assets/track.js` | 全ページ共通。**GA4/Pixelとは別系統**で、既存の gtag 呼び出しには触っていない |
| `POST /api/ev` | 収集の受け口。**無認証**（`middleware.ts` の `PUBLIC_API`）。正規化はここの責任 |
| `event_daily`（D1） | 日付×イベント×発火場所×流入元で**1行に畳む**。個票は持たない |
| `GET /api/insights` | 自前の集計。畳み方の定義はこのファイル1か所 |
| `GET /api/ga4` | GA4 Data API の集計（11章） |

### リンク側の約束

計測したいリンクには、次のどれかを付ける。**track.js はこれしか見ない。**

- `data-ev="<イベント名>"` ＋ `data-ev-label="<発火場所 or 行き先>"` … LP・links.html
- `data-cta="form|line"` ＋ `data-cta-label="<発火場所>"` … メディア（既存の記法をそのまま流用）
- `data-follow="<行き先>"` … メディア（同上）

クリックで拾えないもの（フォーム送信の完了など）は、**読み込み順に依存しない待ち行列**を使う：

```js
(window.annivQueue = window.annivQueue || []).push(['form_complete', 'contact_form']);
```

### 無認証の書き込み口として守っていること

`/api/ev` は文字列を受けて行を作るので、放っておくと `event_daily` の行が無限に増える。
**受け口で必ず正規化する**（`src/pages/api/ev.ts`）：

- `name` は許可リストのみ。未知の名前は**行を作らずに捨てる**（4章の表と対）
- `label` / `campaign` は `[a-z0-9_-]` に落として32字で切る
- `source` は**「指定なし＝`direct`」と「知らない値＝`other`」を区別する**。両方 `direct` に倒すと、
  知らない流入が「直接アクセス」に化ける
- ボディ512バイトまで／同一IP＋同一イベントは10秒まとめて1件

**ここを緩めるなら、行数がどこまで増えるかを先に考えること。**

### 2つの数字を足さない

`/dashboard` の Measurement 欄は、自前とGA4を**列を分けて**出している。
セッションの定義も計測タイミングもブロッカーの影響も違うので、**必ずズレる**。
片方をもう片方で補正しようとすると両方信用できなくなる。

- **自前** … 仕込んだ導線の成果（クリック・CV・記事PV）
- **GA4** … 母数と流入の内訳（セッション・参照元）

## 9. 計測の限界（把握しておくこと）

- **LINEの友だち追加数はサイト側では取れない。** `lin.ee` の短縮URLにはパラメータを付けられないため、こちらで分かるのは「サイトのどこからLINEへ飛んだか」（`line_add_click` の label）まで。**実際に友だちになったかは LINE Official Account Manager 側でしか見えない**。この2つの数字は一致しない前提で扱う
- **Meta Pixel はブラウザのトラッキング防止・広告ブロッカーで欠損する。** GA4も同様。絶対値ではなく傾向で見る
- **`form_complete` は送信成功のレスポンスを受けた時点で発火する。** 実際にメールが届いたかまでは保証しない

## 10. 今後足すもの

- 記事一覧→記事のクリック計測（今は入れていない。GA4のページ遷移で追えるため優先度低）
- **メディア→CVの接続**: 自前計測を入れたことで**流入元つきで `form_complete` が数えられるようになった**（8章）。
  ただし取れるのは `utm_source`（SNS・広告・検索）までで、**「どの記事から相談に来たか」はまだ分からない**。
  記事ごとに見たくなったら、記事内のCTAリンクに `utm_campaign=<slug>` を付けるのが最小の追加
- **SNSの指標（フォロワー推移・投稿別）をダッシュボードに合流させる**。
  `SNS_DB` バインディングで multi-SNS-manager の D1 を読む経路は `/api/sns-cost` で動いているので、
  同じやり方で `account_metrics` / `post_metrics` を引ける。**あちらの実APIでの取得が通ってから**着手する
  （2026-08-28 時点で Instagram のインサイトは実API未検証）
- スポンサーリンク・アフィリを入れる場合は、クリック計測を必ずセットで入れる（爆速開発部で外部リンククリックが測れず詰まった箇所）。あわせて `rel="sponsored"` とPR表記もコンポーネント側で強制する

## 11. GA4 Data API の設定（ダッシュボードにGA4の数字を出す）

**2026-08-28 に設定済み。ダッシュボードにセッション数が出ている状態。**
以下は再設定・鍵のローテーション・別環境を作るときの手順として残す。

`/api/ga4` が GA4 から集計を引く。**未設定でも画面は落ちない**（「未設定」と出るだけ）。
**Googleの管理画面での作業なので、CLIからは代行できない。**

### 1. GA4のプロパティIDを控える

GA4 → 管理（左下の歯車）→ プロパティ設定 → 右上の**「プロパティID」**（9桁前後の数字）。
**測定ID（`G-77X1XS59RB`）とは別物。** 数字だけのほうを使う。

### 2. Google Cloud でサービスアカウントを作る

1. https://console.cloud.google.com/ を開く（GA4と同じGoogleアカウントで）
2. 上部のプロジェクト選択 → **「新しいプロジェクト」**。名前は `anniv-ga4` などで作成
3. 左メニュー **「APIとサービス」→「ライブラリ」** → `Google Analytics Data API` を検索 → **有効にする**
4. 左メニュー **「IAMと管理」→「サービスアカウント」** → **「サービスアカウントを作成」**
   - 名前: `anniv-dashboard` → 作成して続行 → ロールは**付けなくていい**（GA4側で権限を渡すため）→ 完了
5. 作ったサービスアカウントをクリック → **「キー」タブ** → 「鍵を追加」→「新しい鍵を作成」→ **JSON** → 作成
   - JSONがダウンロードされる。**このファイルはリポジトリに置かない**
6. JSONの中の `client_email`（`...@....iam.gserviceaccount.com`）と `private_key` を使う

### 3. GA4側でそのサービスアカウントに閲覧権限を渡す

GA4 → 管理 → **プロパティのアクセス管理** → 右上の「＋」→ 「ユーザーを追加」
→ メールに **手順2の `client_email`** を貼る → 役割は **「閲覧者」** → 追加。

**ここを忘れると鍵が正しくても 403 になる。**

### 4. 値をシークレットに入れる

```bash
npx wrangler secret put GA4_PROPERTY_ID
npx wrangler secret put GA4_SA_EMAIL
npx wrangler secret put GA4_SA_PRIVATE_KEY
```

`GA4_SA_PRIVATE_KEY` は JSON の `private_key` の値を**そのまま**（`-----BEGIN PRIVATE KEY-----` から
`-----END PRIVATE KEY-----` まで）貼る。**JSON中の `\n` は変換しなくてよい**（`src/lib/ga4.ts` が戻す）。

ローカルで試すときは `.dev.vars` に同じ3つを書く（`.gitignore` 済みであることを確認する）。

### 5. 確認

`/dashboard` を開いて Measurement 欄の「セッション（GA4）」に数字が出れば通っている。
出ない場合、サブテキストに理由が出る：

| 表示 | 原因 |
|---|---|
| `GA4_PROPERTY_ID などが未設定` | シークレットが入っていない／プロパティIDが数字でない |
| `認証に失敗（鍵かGA4側の権限）` | 鍵が壊れている、または手順3をやっていない |
| `GA4への問い合わせに失敗` | プロパティIDが違う／APIが有効になっていない |

**GA4のAPIには日次クォータがある**ので、集計は Worker 側で10分キャッシュしている。
値が古く見えるのはそのため。
